1 · What a firewall actually does

Think of a firewall as the bouncer at the door of your network. Every packet of data trying to enter, leave, or cross between network segments has to show the bouncer its ID: where are you from, where are you going, and what are you carrying?

A next-generation firewall (NGFW) like FortiGate is a bouncer with a brain. A basic firewall only checks the envelope — source IP, destination IP, port number. An NGFW opens the envelope: it can spot viruses (antivirus), block known attack patterns (IPS — intrusion prevention), filter websites by category (web filter), and recognize applications (application control). Fortinet bundles these as UTM profiles (Unified Threat Management) that you attach to a policy.

LOGIC CHECK: If a firewall only checked IP addresses, could it stop malware hidden inside an allowed web download? No — the envelope looks fine. That gap is exactly why NGFWs inspect content, not just headers.

2 · Policy order: first match wins

FortiGate evaluates firewall policies top-down, in order, and stops at the first match. It does not keep looking for a "better" match below.

policy 1: LAN -> WAN, service ALL, action DENY ← evaluated first policy 2: LAN -> WAN, service HTTP/HTTPS, action ACCEPT ← never reached!

In the example above, web traffic from the LAN is blocked — policy 1 matches everything from LAN to WAN and denies it, so policy 2 never gets a say. This is the single most common firewall misconfiguration in the field, and it will show up on your assessment.

LOGIC CHECK: Rules are read like a recipe, top to bottom. The golden order is: specific allows at the top, general denies at the bottom. A deny-all at the very bottom is your safety net — it catches everything you forgot to allow on purpose.

3 · UTM profiles: the NGFW brain

When a policy's action is accept, you can bolt on inspection profiles. Each one answers a different question about the traffic:

  • Antivirus (AV) — "Does this file contain known malware?" Scans downloads, email attachments.
  • IPS (Intrusion Prevention) — "Does this traffic match a known attack signature?" Blocks exploits, scans, brute-force patterns.
  • Web Filter — "Is this website in an allowed category?" Blocks gambling, malware sites, etc. by category or URL.
  • Application Control — "Which application is this, really?" Identifies apps even on non-standard ports.

In FortiOS you enable them per-policy (set utm-status enable), because deep inspection costs CPU — you inspect where it matters (user web traffic), not everywhere (backup replication between servers).

LOGIC CHECK: UTM profiles only make sense on accept policies. Inspecting traffic you are about to deny is wasted work — deny first, inspect what you allow.

4 · NAT: one public IP, many private devices

Your LAN uses private addresses (192.168.1.x) that the internet cannot route. NAT (Network Address Translation) rewrites addresses as packets cross the firewall:

  • Source NAT (SNAT) — outbound. Fifty LAN PCs browse the web; the firewall rewrites every source IP to its single public WAN IP. The internet replies to the firewall, which un-rewrites and delivers. In FortiOS: set nat enable on the policy.
  • Destination NAT (DNAT / VIP) — inbound. A public IP:port maps to a private server (config firewall vip). Internet users hit 203.0.113.10:443 and reach your DMZ web server at 10.10.10.50:443.
LOGIC CHECK: NAT is stateful — the firewall remembers each translation, so reply traffic is un-NATed automatically. You never write a second rule for the return path. If return traffic needed its own rule, every web session would need two policies.

5 · Zones, interfaces & direction

FortiGate policies are directional: every policy has a source interface and a destination interface (set srcintf / set dstintf). Interfaces play zone roles:

port1 192.168.1.1/24 LAN (trusted users) port2 203.0.113.2/24 WAN (untrusted internet) port3 10.10.10.1/24 DMZ (public servers, semi-trusted)

A policy srcintf port1 dstintf port2 governs LAN→WAN only. Return traffic is handled by the session table, not by a mirror policy. Traffic the firewall itself may receive (ping, HTTPS admin) is controlled separately per-interface with set allowaccess — and you keep that list tiny.

The implicit deny

After the last policy, FortiOS has a built-in implicit deny — anything unmatched is dropped silently. Best practice is an explicit deny-all policy at the bottom anyway, so the drop is logged and visible in hit counts instead of vanishing.

Lab 1 (guided) — Allow web from LAN to WAN, block everything else

Build it in the CLI Terminal tab (or Quick-add on the Policy Board). The baseline already has an explicit deny-all at the bottom — your job is the allow rule above it.

  1. config firewall policy — enter the policy table.
  2. edit 2 — create policy #2. New policies land at the bottom of the list — notice where that puts it relative to deny-all.
  3. Set the fields: set srcintf port1, set dstintf port2, set service "HTTP" "HTTPS", set action accept, set nat enable.
  4. next then end — save and exit.
  5. config firewall policy again, then move 2 before 1 — slide your allow rule above deny-all. First match wins, so order is everything.
  6. Send an HTTPS packet from 192.168.1.50 on the Policy Board and confirm it is ACCEPTED by your new policy.
LOGIC CHECK: Why does the allow rule have to be above deny-all? Because evaluation stops at the first match. If deny-all sits on top, your allow rule is decoration — correct config, wrong order, still broken.

Lab 2 (challenge) — The case of the dead web browser

Incident: "Nobody on the LAN can browse the web since last night's change window. The allow rule is right there in the config!" Load the broken config, diagnose with the packet tester, fix it, then verify.

LOGIC CHECK: show firewall policy tells you what exists; diagnose firewall policy list tells you what is firing. When traffic misbehaves, hit counts are your witness — the rule with climbing hits is the one making the decision.
