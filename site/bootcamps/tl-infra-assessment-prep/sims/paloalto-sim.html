1 · PAN-OS in 60 seconds

Palo Alto firewalls run PAN-OS. Instead of thinking in interfaces first (like FortiGate's port1 → port2), PAN-OS thinks in zones first: every interface belongs to a zone, and every security rule says which zones traffic may cross. The classic trio:

Trust
Your inside network. User PCs, internal servers. 10.0.1.0/24 here.
DMZ
"Demilitarized zone" — servers the public must reach (web, mail) but that you still don't fully trust. 10.0.2.0/24 here.
Untrust
The internet. Assume hostile.
Rule of thumb
Traffic between zones is inspected. Traffic inside one zone flows freely unless you say otherwise.

Policies live on the Security tab of the rulebase and are evaluated top-down, first match wins — the same universal principle as FortiGate. NAT lives on its own NAT tab, evaluated before the security rules.

2 · App-ID: applications, not ports

This is Palo Alto's signature idea. A traditional firewall rule says "allow TCP port 443" — it checks the envelope. App-ID identifies the application itself by inspecting the traffic's behavior and signatures, regardless of which port it uses.

Port-based thinking: allow tcp/443 -> allows EVERYTHING on 443 (web browsing... but also malware C2, rogue VPNs, tunneled file sharing) App-ID thinking: allow application "web-browsing" -> allows real web browsing on ANY port -> still blocks look-alikes on 443

Real example: a user runs a web app on TCP 8080 instead of 443. A port-based rule for 443 misses it entirely (broken app, confused admin). An App-ID rule for web-browsing with service application-default still recognizes and allows it — you'll prove this to yourself in the lab.

LOGIC CHECK: If your rule says "allow tcp/443", you have allowed every application capable of using port 443 — including the ones you meant to block. Ports describe where traffic goes; App-ID describes what it is. Assessments love this distinction: "Why is application-based policy safer than port-based?" — this is the answer.

3 · Anatomy of a security rule

Every PAN-OS security rule answers six questions, in order:

  • Name — human-readable, e.g. allow-web-trust-to-untrust.
  • From / To zone — e.g. Trust → Untrust. Directional, like FortiGate's srcintf/dstintf.
  • Source / Destination — addresses or any.
  • Application — the App-ID star of the show (web-browsing, dns, any…).
  • Service — usually application-default ("whatever ports this app normally uses"); can pin specific ports when you must.
  • Action — allow, deny (sends a reset/unreachable so the sender knows), or drop (silent — the packet vanishes, slower for scanners to probe).
LOGIC CHECK: deny vs drop: deny is polite but chatty (tells the sender "no"), drop is silent but stealthy. Facing the internet, security teams often prefer drop — why confirm to an attacker that you exist?

4 · NAT on its own tab

Unlike FortiGate (where you tick set nat enable on the policy), PAN-OS keeps NAT rules on a separate NAT tab, evaluated before security policy:

  • Source NAT — Trust users go out to Untrust; their 10.0.1.x source becomes the firewall's public IP. ("Hide NAT" / interface-address.)
  • Destination NAT — the public IP 203.0.113.10 becomes DMZ server 10.0.2.50 before the security rule is checked — so the security rule's destination zone is DMZ, the post-NAT zone.
LOGIC CHECK: Order of operations is NAT then security policy. If you write the security rule against the pre-NAT address, it will never match — the address was already rewritten. Always think: "what does the packet look like after NAT?"

5 · VPN on PAN-OS: same ideas, different boxes

A site-to-site IPsec tunnel needs the same two phases you saw on FortiGate — PAN-OS just names the objects differently:

  • Tunnel interface — a virtual interface the encrypted traffic flows through.
  • IKE Gateway — "who am I talking to" (peer IP, pre-shared key, IKE crypto) ≈ FortiGate phase 1.
  • IPsec Tunnel — "what traffic goes inside" (local/remote networks, IPsec crypto) ≈ FortiGate phase 2.

Different labels, identical logic: authenticate the peer, agree on crypto, define interesting traffic. Learn the logic once and every vendor's VPN becomes translation, not re-learning.

Guided lab — application-based allow for web-browsing, Trust → Untrust

Use the Policy Builder tab to create the rule, then come back and verify. The point of this lab: prove to yourself that App-ID doesn't care about ports.

  1. Create a rule named allow-web-trust-to-untrust: from Trust, to Untrust.
  2. Set Application to web-browsing (not any) and Service to application-default.
  3. Set Action to allow with logging on, then Commit. It must land above the final deny.
  4. The proof: send web-browsing on TCP 8080 (non-standard port) from Trust on the Zones tab — App-ID still recognizes and allows it.
LOGIC CHECK: A port-based rule (any app + tcp/443) would have missed that 8080 flow entirely. Application-based policy is why Palo Alto gear is bought: policy follows the application, not the port number it happened to use today.

"A bank SOC needs to allow Salesforce but block everything else Salesforce-shaped, with full audit trails." That's the application-identity + change-control play.
