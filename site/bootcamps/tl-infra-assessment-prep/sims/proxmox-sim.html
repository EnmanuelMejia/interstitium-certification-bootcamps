LXC CONTAINERS

LXC Containers vs Virtual Machines — from zero

A virtual machine virtualizes hardware: every VM boots its own full operating system with its own kernel. An LXC container virtualizes the operating system: containers share the host's Linux kernel and just get isolated slices of it (their own filesystem, processes, and network).

KVM VIRTUAL MACHINE
  • Own virtual hardware: vCPU, virtual disk, virtual NIC
  • Own kernel — can run Windows, BSD, any Linux
  • Strong isolation (hardware boundary)
  • Heavier: each VM needs its own RAM for a full OS (1–2 GB+ just to idle)
  • Boots in ~20–60 seconds
  • Managed with qm commands
LXC CONTAINER
  • Shares the host kernel — Linux guests only
  • No virtual hardware; processes run natively on the host CPU
  • Featherweight: a container can idle on ~50 MB of RAM
  • Starts in ~1–2 seconds
  • Perfect for: DNS servers, reverse proxies, monitoring, small services
  • Managed with pct commands
🔍 LOGIC CHECK
If a container shares the host's kernel, could it run Windows? No — Windows needs its own kernel, which only a full VM provides. Rule of thumb: Linux service, lightweight → LXC. Windows, or needs its own kernel → VM. Interviewers love this exact question.

Try it: pct commands in the CLI

Open the CLI Console tab and run pct list, then create one: pct create 210 debian-12 --hostname dns01 --memory 512 — then pct start 210. Watch it appear in the Web UI tree.

WHEN TO USE WHICHVM: Windows Server, appliances needing a custom kernel, untrusted workloads, anything needing full isolation. LXC: fleets of small Linux services — you can run 5× more containers than VMs on the same hardware.

Core Concepts — from absolute zero

Read these in order. Each answers what it is, how it works, why it exists, and when you meet it.

1 · Type-1 hypervisor

What: Software that lets one physical server run many virtual servers. How: A Type-1 ("bare-metal") hypervisor installs directly on the hardware — there is no Windows or desktop underneath. Proxmox VE is a Type-1 hypervisor (its base is Debian Linux, but it boots straight into the hypervisor). Contrast with Type-2 (VirtualBox, VMware Workstation), which run as apps inside a desktop OS.

WHY IT MATTERSType-1 is faster and more stable — nothing competes with the VMs for resources. Every production datacenter uses Type-1. If an interviewer asks "Proxmox: Type-1 or Type-2?" the answer is Type-1, bare metal.

2 · KVM vs LXC — the two engines inside Proxmox

What: Proxmox ships two virtualization engines. KVM (Kernel-based Virtual Machine) turns Linux into a hypervisor for full VMs. LXC (Linux Containers) provides OS-level containers. How: One web UI and one CLI family (qm for KVM, pct for LXC) manage both. When: you pick per workload — see the LXC vs VM tab.

3 · Network bridges — vmbr0

What: A Linux bridge is a virtual switch built in software. vmbr0 is Proxmox's default bridge, bound to the physical network card. How: You plug each VM's virtual NIC into a bridge, exactly like plugging a cable into a switch port. VMs on the same bridge talk to each other; if the bridge is tied to the physical NIC, they also reach the LAN and internet.

🔍 LOGIC CHECK
Want an isolated lab network (VMs talk to each other but not the outside world)? Create a second bridge — vmbr1 — with no physical port attached. It's a switch with no uplink cable: traffic stays inside the host. This is exactly what the guided lab builds.

4 · Storage pools

What: Named places where VM disks, ISOs, and backups live. How: Proxmox defaults: local (ISOs, templates, backups — a directory) and local-lvm (thin-provisioned space for VM disks). Bigger setups add NFS shares or Ceph distributed storage so disks survive a node failure.

WHEN YOU MEET ITDuring VM creation you pick a storage target for the disk. Rule: ISOs live on local; VM disks go on local-lvm (fast, thin). Backups go wherever has space.

5 · Live migration

What: Moving a running VM from one physical node to another with no downtime. How: Memory pages are copied while the VM keeps running; at the final instant the VM is paused for milliseconds and the last changes transfer. Why: hardware maintenance without outages. When: you need it only in a cluster (2+ nodes) with shared storage — a VM's disk must be reachable from both nodes, otherwise there is nothing to migrate to.

🔍 LOGIC CHECK
Live migration moves the running state (RAM/CPU), not the disk — that is why shared storage is the prerequisite. No shared storage → you can only do an offline move (shut down, copy disk, start).

6 · Clustering & quorum

What: Joining Proxmox nodes into one managed cluster with a single web UI. How: pvecm commands join nodes; they elect a leader via quorum — more than half the nodes must agree, so a 2-node cluster that splits can't both think they're in charge (split-brain). Why: one pane of glass, HA failover, migration.

    🔍 LOGIC CHECK
    Why does this course teach Proxmox first? Because the concepts transfer: bridges ≈ virtual switches, storage pools ≈ datastores, live migration ≈ vMotion/Live Migration. Learn the idea once on free software, then map the vocabulary in an interview: "In Proxmox that's a Linux bridge; in Hyper-V you'd call it a virtual switch." That sentence is worth more than memorizing three consoles.
    INTERVIEW FRAMINGNever trash a vendor's product in an interview. Frame it as fit: "ESXi dominates large VMware shops; Hyper-V is natural where Windows Server licensing already exists; Proxmox gives small teams enterprise features — HA, replication, backups — at open-source cost."
