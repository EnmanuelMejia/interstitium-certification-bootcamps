🔍 LOGIC CHECK
Git has three places your work can be: working directory (edited, unsaved), staging area (marked for the next commit via git add), and commits (permanent snapshots via git commit). git status tells you which files are in which place. If you remember nothing else, remember the three places.

🐙 GitHub Concepts

Git = the version-control tool on your machine. GitHub = the website where Git repos live so teams can collaborate. Same relationship as "email program" vs "Gmail".

Repositories

A repo is a project folder with history. On GitHub each repo gets a page: code, branches, commit history, and a README that renders as the project's front door. Clone copies it to your machine; push sends your commits up; pull brings others' commits down.

Issues

A to-do list attached to the repo. Each issue has a number, a title, and a discussion thread — e.g. #42 "VPN drops every 2 hours". Teams link commits to issues ("fixes #42") so history explains why code changed.

Pull Requests — try the simulated flow

A pull request (PR) says: "here are my branch's changes — review them, then merge into main." It's how teams gatekeep quality: discussion + automated checks before code lands.

Actions basics

GitHub Actions runs automation when things happen in the repo — e.g. "on every PR, run the tests; on every merge to main, deploy." The recipe is a YAML file in .github/workflows/:

# .github/workflows/ci.yml — runs on every pull request
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4   # get the PR's code
      - run: ./run-tests.sh          # your checks
WHY INFRA TEAMS CAREThat same pipeline can validate Terraform (terraform plan) on every PR and apply on merge — infrastructure changes get the same review + automation as app code. That's the seed of GitOps.

    💡 Why Git matters for infrastructure

    Infrastructure as Code (IaC)

    Modern infrastructure is defined in text files — Terraform files describe servers, Ansible playbooks describe configuration. Those files live in Git, so every infrastructure change is reviewed (PR), tested (Actions), and reversible (git revert) exactly like application code. "Who changed the firewall rule last Tuesday?" → git log answers in seconds.

    # main.tf — a server, described in text, versioned in Git
resource "proxmox_vm_qemu" "web" {
  name   = "lab-web"
  target_node = "pve01"
  cores  = 2
  memory = 2048
}

    Documentation in Git

    Runbooks, network diagrams-as-code, incident timelines — when docs live in Git next to the infrastructure they describe, they stay current: the PR that changes the system also updates the doc, or review blocks it. Stale wiki pages are how outages repeat.

    🔍 LOGIC CHECK
    Why not just keep configs on the server and docs in a wiki? Because then change has no history: no author, no reason, no rollback. Git gives every change a who, when, and why — which is precisely what an auditor, an incident review, and your future self at 3 AM all need.
